backtest-lib v0.1.0

Librairie locale pour le téléchargement de données de marché (crypto via ccxt, actions via yfinance/IBKR) avec cache Feather, backtest vectorisé (vectorbt) et analyse des résultats.

Installation

La librairie est installée en mode éditable depuis le répertoire source. Toute modification dans les fichiers source est immédiatement disponible sans réinstallation.

# Depuis le dossier du projet
pip install -e /home/faucheur/code/backtest

# Import dans n'importe quel script
from data_manager import DataManager, CCXTProvider, YFinanceProvider
from backtest_vectorbt import TradingSimulator
from backtest_analysis import BacktestAnalyzer
Mode éditable (-e) pip pointe directement vers le dossier source. Pas besoin de réinstaller après chaque modification.

DataManager

class DataManager
from data_manager import DataManager

Façade unique au-dessus de plusieurs sources de données OHLCV (ccxt, yfinance, IBKR). Délègue le téléchargement à un Provider et persiste les résultats dans un cache local Feather. Récupération incrémentale : seuls les intervalles non couverts par le cache sont demandés au provider.

__init__

DataManager(provider: Provider, data_dir: str = "data")

Construit le gestionnaire à partir d'un provider de données et d'un répertoire de cache.

ParamètreTypeDescriptionDéfaut
provider requisProvider Instance d'un provider concret : CCXTProvider, YFinanceProvider, IBKRProvider, ou un provider custom (voir Provider). —
data_dir optionnelstr Répertoire de cache Feather. Créé s'il n'existe pas. Nommage : <symbol>_<timeframe>_<source>.feather. "data" 
dm = DataManager(CCXTProvider("binance"))                # crypto explicite
dm = DataManager(CCXTProvider(), data_dir="./data")       # crypto fallback auto
dm = DataManager(YFinanceProvider())                       # actions / ETF

get

dm.get(symbol: str, timeframe: str, start: str|int|float|datetime, end=None, validate=True) → DataFrame

Charge les bougies OHLCV pour un symbole sur une plage donnée. Si end est omis, start est interprété comme une durée glissante (ex : "3mois") et la plage devient [now − duration, now].

ParamètreTypeDescriptionDéfaut
symbol requisstrIdentifiant accepté par le provider. Ex : "BTC/USDT" (ccxt), "MSTR" (yfinance), "AAPL" ou ib_insync.Contract (ibkr).—
timeframe requisstrRésolution des bougies. Format propre à chaque provider — voir leurs sections respectives.—
start requisstr | int | float | datetime Soit une date (ISO "2024-01-01", timestamp secondes/ms, ou datetime), soit — quand end=None — une durée glissante : "30d", "3mois", "1y", "6h", etc. —
end optionnelstr | int | float | datetimeDate de fin. Si omis, start est traité comme une durée et end = now.None
validate optionnelboolAppelle provider.validate(symbol) avant le fetch (peut faire un appel réseau). Mettre à False si déjà validé en amont.True
Retourne
pd.DataFrame indexé par DatetimeIndex UTC, colonnes open, high, low, close, volume. 
# Plage explicite
df = dm.get("BTC/USDT", "1h", "2024-01-01", "2024-06-01")

# Durée glissante
df = dm.get("BTC/USDT", "1h", "3mois")
Formats de durée acceptés "30min", "6h", "7j" / "14d", "2w", "3mois", "1an" / "2y". Espaces tolérés. 1 mois = 30 jours, 1 an = 365 jours (pas de calcul calendaire).

get_many

dm.get_many(symbols: List[str], timeframe: str, start, end=None, max_workers=1, validate=True) → Dict[str, DataFrame]

Version batch de get. Avec max_workers > 1, les téléchargements sont parallélisés via ThreadPoolExecutor ; chaque worker reçoit une deepcopy du provider pour ne pas partager l'état interne (sessions HTTP, cache markets ccxt, etc.). Une barre de progression rich est affichée pendant l'exécution.

ParamètreTypeDescriptionDéfaut
symbols requisList[str]Liste de symboles, même format que pour get.—
timeframe requisstrTimeframe commun à tous les symboles.—
start requisstr | int | float | datetimeDate ou durée glissante (cf. get).—
end optionnelstr | int | float | datetimeDate de fin, ou None pour utiliser start comme durée.None
max_workers optionnelintThreads parallèles. 1 = séquentiel. Recommandé : 4–8 selon la limite de taux du provider.1
validate optionnelboolValide chaque symbole avant le batch.True
Retourne
Dict[str, pd.DataFrame] — clé = symbole, valeur = DataFrame OHLCV. L'ordre des clés respecte celui de la liste symbols. 
symbols = ["BTC/USDT", "ETH/USDT", "SOL/USDT"]
data = dm.get_many(symbols, "1h", "2024-01-01", "2024-12-31", max_workers=4)
btc_df = data["BTC/USDT"]

Limites et comportements à connaître

SujetComportement
Cache incrémental Le cache vérifie si la plage demandée est déjà couverte. Si oui, retour direct sans appel réseau. Sinon, seuls les intervalles manquants aux bords (avant min, après max du cache) sont demandés au provider. Les trous internes ne sont pas comblés (hypothèse : séries continues pour un timeframe donné).
Cache partagé par (symbol, timeframe, source) Un fichier <symbol>_<timeframe>_<source>.feather par triplet. Le source vient de provider.name (ex : binance, yfinance, ibkr), donc les caches restent séparés si on change de provider pour un même symbole.
Tolérance bougie en cours Le dernier intervalle est considéré couvert si le cache se termine à moins d'un timeframe de l'instant présent — évite de retélécharger une bougie en formation. Calculé via parse_timeframe de ccxt quand le provider est un CCXTProvider, sinon désactivé.
Durées glissantes Quand end=None, start est parsé comme une durée. Formats acceptés : "30min", "6h", "7j" / "14d", "2w", "3mois", "1an" / "2y". Espaces tolérés. 1 mois = 30 jours fixes, 1 an = 365 jours fixes.
Erreurs en mode parallèle Avec max_workers > 1, tous les symboles sont tentés avant remontée d'erreur. Si au moins un échoue, un RuntimeError est levé à la fin avec la liste des symboles en échec ; les résultats partiels ne sont pas retournés.
Timeframes Validation déléguée au provider. Voir les sections CCXTProvider, YFinanceProvider, IBKRProvider pour les valeurs supportées.

Providers

module data_manager.providers
from data_manager import CCXTProvider, YFinanceProvider, IBKRProvider

Chaque provider encapsule l'accès à une source de données et expose une interface uniforme (name, fetch, validate) consommée par DataManager. Ajouter un nouveau provider revient à sous-classer Provider et implémenter fetch.

CCXTProvider

CCXTProvider(exchange: Optional[str] = None)

Provider crypto basé sur ccxt. Deux modes :

  • Explicite : CCXTProvider("binance") — utilise un exchange donné.
  • Auto : CCXTProvider() — essaie les exchanges de FALLBACK_EXCHANGES dans l'ordre et prend le premier qui supporte le symbole. L'exchange est résolu lazy au premier validate/fetch, puis figé pour la session.
ChampTypeDescription
FALLBACK_EXCHANGESList[str]Ordre par défaut : ["binance", "bybit", "kraken", "okx", "coinbase", "kucoin"].
namestrEn mode explicite, l'id ccxt. En mode auto avant résolution : "ccxt_auto" ; après résolution : l'id de l'exchange retenu.

Timeframes : délégués à ccxt ("1m", "5m", "1h", "4h", "1d", etc.). Voir exchange.timeframes pour le détail par exchange.

Retry : les erreurs NetworkError, RequestTimeout, RateLimitExceeded, ExchangeNotAvailable sont réessayées (backoff exponentiel, max 5 tentatives). 

# Explicite
prov = CCXTProvider("kraken")
dm = DataManager(prov)

# Auto fallback
dm = DataManager(CCXTProvider())
btc = dm.get("BTC/USDT", "1h", "30d")  # résout binance au premier appel
Spot uniquement La validation rejette les marchés futures/perpetual/swap. Utiliser "BTC/USDT" et pas "BTC/USDT:USDT".

YFinanceProvider

YFinanceProvider()

Provider actions / ETF / indices via yfinance. Requiert pip install yfinance.

ChampTypeDescription
namestr"yfinance"

Timeframes supportés : "1m", "2m", "5m", "15m", "30m", "1h" / "60m", "90m", "1d", "5d", "1w" / "1wk", "1mo", "3mo".

IBKRProvider(host="127.0.0.1", port=4002, client_id=None, what_to_show="TRADES", use_rth=True, timeout=15.0)

Provider Interactive Brokers via ib_insync. Requiert TWS ou IB Gateway lancé et logué, avec API socket activée.

ParamètreTypeDescriptionDéfaut
hoststrHôte du socket TWS/Gateway."127.0.0.1"
portint4002 = IB Gateway paper, 4001 = Gateway live, 7497 = TWS paper, 7496 = TWS live.4002
client_idintSi None, un ID aléatoire (1000–9999) est tiré pour éviter les collisions.None

Symboles : par défaut, le symbole est résolu en Stock(symbol, "SMART", "USD"). Pour futures / forex / options, passer un objet ib_insync.Contract directement comme symbol. 

from data_manager import DataManager, IBKRProvider

prov = IBKRProvider(port=4002)  # Gateway paper
dm = DataManager(prov)
df = dm.get("AAPL", "1h", "30d")
Connexion persistante Une seule connexion socket est réutilisée entre les fetch. En mode parallèle (get_many), chaque worker reçoit un provider via deepcopy qui crée une nouvelle instance non connectée avec un client_id différent.

TradingSimulator

class TradingSimulator
from backtest_vectorbt import TradingSimulator

Moteur de backtest vectorisé basé sur vectorbt. Encapsule la construction du portefeuille, le calcul des métriques de performance (Sharpe, drawdown, beta, win rate…) et l'export des résultats. Conçu pour fonctionner avec un objet strategy qui expose les méthodes prepare_data et generate_signals.

ts.run_simulation(symbol: str, data_dict: dict, params=None, reload=False) → dict

Lance la simulation pour un seul symbole. Si un fichier .pkl existe déjà pour ce symbole/stratégie et que reload=False, le portfolio est rechargé depuis le disque sans recalcul.

ParamètreTypeDescriptionDéfaut
symbol requisstrPaire de trading, ex : "BTC/USDT".—

reload optionnelboolSi True, force le recalcul même si un .pkl existe.False
Retourne
{"symbol": str, "portfolio_data": dict} où portfolio_data contient :

  • annualized_return, sharpe_ratio, beta_underlying

run_batch_simulations

ts.run_batch_simulations(symbols: List[str], data_dict: dict, params=None, reload=False) → Tuple[dict, dict]

Lance les simulations en parallèle sur tous les symboles via ProcessPoolExecutor (18 workers hardcodés). Les erreurs par symbole sont catchées et loggées sans interrompre le batch.

Attention — ProcessPoolExecutor Le code de la stratégie et du config doit être picklable (pas de lambdas, pas de closures non sérialisables). Ce point d'entrée est conçu pour des runs sur un grand nombre de symboles (20+).
Retourne
(results, portfolios_data) — deux dicts avec le symbole comme clé. portfolios_data est directement passable à export_results_to_json. 
results, portfolios_data = ts.run_batch_simulations(
    symbols, data_dict, params=params, reload=False
)
ts.export_results_to_json(portfolios_data, symbols)

Quickstart complet

from data_manager import DataManager, CCXTProvider
from backtest_vectorbt import TradingSimulator
from backtest_analysis import BacktestAnalyzer

# 1. Télécharger les données
dm = DataManager(CCXTProvider("binance"), data_dir="./data")
symbols = ["BTC/USDT", "ETH/USDT", "SOL/USDT"]
data_dict = dm.get_many(symbols, "1h", "3mois", max_workers=3)

# 2. Configurer la simulation
class Config:
    PORTFOLIO_DIR = "backtests/portfolios"
    default_params = {
        "capital_initial": 10_000,
        "fees": 0.001,
        "slippage_base": 0.0,
        "timeframe": "1h",
    }

ts = TradingSimulator(config=Config(), strategy=my_strategy)

# 3. Lancer le backtest
results, portfolios_data = ts.run_batch_simulations(symbols, data_dict)

# 4. Exporter les résultats
output = "backtests/results/results.json"
ts.export_results_to_json(portfolios_data, symbols, output_path=output)

# 5. Analyser et générer les graphiques
analyzer = BacktestAnalyzer(summary_path=output)
stats = analyzer.run()

Écrire une stratégie compatible

TradingSimulator délègue la préparation des données et la génération des signaux à un objet strategy. Celui-ci doit implémenter deux méthodes :

Interface attendue

class MyStrategy:
    name = "MyStrategy"  # Utilisé pour nommer les fichiers .pkl

    def prepare_data(self, data_dict: dict, symbol: str):
        """
        Prépare et enrichit le DataFrame pour un symbole donné.

        Paramètres :
          data_dict : dict {symbol: DataFrame} retourné par DataManager
          symbol    : paire courante ex "BTC/USDT"

        Doit retourner : (data, asset_name)
          data       : pd.DataFrame avec au moins une colonne nommée asset_name
          asset_name : str, nom de la colonne prix (ex "BTC")
        """
        df = data_dict[symbol].copy()
        asset_name = symbol.split("/")[0]
        df[asset_name] = df["close"]
        return df, asset_name

    def generate_signals(self, data: pd.DataFrame, asset_name: str, params: dict):
        """
        Génère les signaux d'entrée/sortie.

        Doit retourner un tuple de 3 ou 5 éléments :
          (data, entries, exits)                              — long only
          (data, entries, exits, short_entries, short_exits)  — long + short

        entries / exits : pd.Series ou pd.DataFrame de booléens,
                          indexés comme data.
        """
        close = data[asset_name]
        sma20 = close.rolling(20).mean()
        sma50 = close.rolling(50).mean()

        entries = (sma20 > sma50) & (sma20.shift(1) <= sma50.shift(1))
        exits   = (sma20 < sma50) & (sma20.shift(1) >= sma50.shift(1))

        return data, entries, exits
Convention de nommage des colonnes Le simulateur cherche une colonne dont le nom est asset_name (ex : "BTC") dans le DataFrame. Si elle est absente, il replie sur "close". Assure-toi que prepare_data crée cette colonne.
Signaux booléens entries et exits peuvent être des pd.Series, pd.DataFrame ou des arrays numpy. La méthode interne _to_bool_frame les normalise automatiquement.
